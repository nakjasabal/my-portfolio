# Codex 첫 사용 안내서

Codex는 대화만 하는 도구가 아니라, 선택한 프로젝트 폴더의 파일을 읽고 수정하며 필요한 명령을 실행해 개발 작업을 함께 처리하는 AI 에이전트입니다. 처음에는 “무엇을 만들거나 고치고 싶은지”를 말하고, Codex가 제안·수정한 내용을 확인하는 방식으로 쓰면 됩니다. 이 문서는 데스크톱 앱, IDE 확장, 터미널에서 공통으로 적용되는 가장 기본적인 사용법을 정리합니다.

> 핵심 원칙: Codex에게 목표와 완료 기준을 알려주고, 중요한 변경은 직접 검토한 뒤 반영합니다.

## 1. 시작하기

### 작업할 폴더를 먼저 정한다

Codex는 현재 열어 둔 프로젝트(워크스페이스)를 중심으로 일합니다. 새 프로젝트라면 빈 폴더를 만들거나 기존 Git 저장소 폴더를 열고, 그 안에서 대화를 시작하세요. 폴더 밖의 파일이나 네트워크 접근처럼 범위를 벗어나는 동작은 권한 확인이 필요할 수 있습니다.

처음에는 작은 작업으로 감을 잡는 것이 좋습니다.

- “이 프로젝트가 무엇을 하는지 `README`와 폴더 구조를 보고 5줄로 설명해줘.”
- “현재 변경된 파일이 있는지 확인하고, 수정하지 말고 요약만 해줘.”
- “`src` 폴더에서 로그인 화면과 관련된 파일을 찾아줘.”

Codex가 코드를 바꾸기 전에 먼저 조사하거나 계획을 만들도록 요청할 수도 있습니다. 여러 파일이 얽히거나 요구사항이 모호한 경우에는 `/plan`을 입력하거나 “수정하지 말고 먼저 구현 계획과 영향 파일을 알려줘”라고 말하세요. 계획을 읽고 방향을 정한 뒤 구현을 맡기면 예상 밖의 변경을 줄일 수 있습니다.

### 첫 번째 실제 요청

간단한 변경은 아래처럼 요청합니다.

```text
README의 실행 방법이 오래되었는지 확인해줘.
필요하면 현재 프로젝트 설정에 맞게 수정하고,
마지막에 바뀐 내용과 확인한 명령을 요약해줘.
```

Codex는 보통 파일을 살펴보고, 필요한 경우 명령 실행 또는 파일 수정을 제안합니다. 진행 중에는 이유와 작업 내용을 읽고, 권한 승인 창이 나타나면 대상과 명령을 확인한 뒤 승인하세요. 모르는 명령이거나 작업 범위와 무관하다면 거절하고 설명을 요청해도 됩니다.

## 2. 좋은 요청을 만드는 네 가지 요소

완벽한 프롬프트가 필요하지는 않지만, 아래 정보가 있으면 결과가 훨씬 안정적입니다.

| 요소 | 알려줄 내용 | 예시 |
| --- | --- | --- |
| 목표 | 무엇을 바꾸거나 만들지 | “회원 가입 시 이메일 형식을 검사해줘.” |
| 맥락 | 관련 파일, 오류, 참고 자료 | “`src/auth`와 이 오류 메시지를 참고해줘.” |
| 제약 | 유지할 규칙, 건드리지 말 것 | “기존 API 형식은 바꾸지 말고 외부 패키지는 추가하지 마.” |
| 완료 기준 | 끝났다고 판단할 조건 | “테스트를 추가하고 관련 테스트가 통과하면 끝내줘.” |

다음 두 요청의 차이를 보세요.

```text
로그인 오류 고쳐줘.
```

```text
로그인 실패 때 화면이 멈추는 문제를 고쳐줘.
재현: 잘못된 비밀번호를 입력한 뒤 다시 시도하면 버튼이 비활성화된 채로 남아.
`src/pages/Login.tsx`와 기존 로그인 테스트를 우선 확인해줘.
API 응답 형식은 바꾸지 말고, 수정 후 관련 테스트를 실행해줘.
```

두 번째처럼 결과·재현 방법·제약·검증을 주면 Codex가 추측할 부분이 적어집니다. 특정 파일을 보고 싶다면 파일을 첨부하거나 경로를 적으세요. 최신 정보가 필요한 작업은 “공식 문서를 검색하고 출처를 함께 알려줘”처럼 명시하는 편이 좋습니다.

## 3. 일하는 기본 흐름: 요청 → 확인 → 검토 → 개선

### 1) 먼저 조사시키기

낯선 코드베이스에서는 바로 “구현해줘”라고 하기보다 구조와 관련 코드를 확인하게 하세요.

```text
이 저장소의 실행·테스트 방법과 주요 폴더를 조사해줘.
아직 파일은 수정하지 말고, 다음 작업을 위한 짧은 안내를 작성해줘.
```

### 2) 계획을 확인한 뒤 구현시키기

작업이 크다면 단계별 계획과 위험 요소를 먼저 받습니다.

```text
다크 모드를 추가하고 싶어. 먼저 관련 컴포넌트, 상태 관리 방식,
수정할 파일 목록, 테스트 방법을 계획으로 제안해줘. 내 확인 전에는 수정하지 마.
```

계획이 맞으면 “그 계획대로 구현해줘. 범위 밖 변경이 필요하면 먼저 물어봐”라고 이어서 요청합니다. 같은 대화에서는 앞선 맥락이 유지되므로, 새로 처음부터 설명할 필요 없이 원하는 수정 사항을 구체적으로 덧붙이면 됩니다.

### 3) 변경 사항과 검증 결과를 검토하기

작업이 끝나면 다음을 요청하는 습관이 좋습니다.

```text
변경한 파일별로 이유를 요약하고, 실행한 테스트와 결과를 알려줘.
실행하지 못한 검증이 있다면 이유와 내가 할 다음 단계를 적어줘.
```

앱이나 IDE에서는 변경(diff) 화면을 열어 줄 단위로 확인할 수 있습니다. 특히 설정 파일, 인증·결제 로직, 데이터 삭제·마이그레이션, 외부 서비스 전송과 관련된 변경은 반드시 읽어 보세요. Git을 쓴다면 작업 전후로 `git status`와 diff를 확인하고, 작은 단위로 커밋하는 것이 안전합니다.

### 4) 피드백으로 다듬기

첫 결과가 기대와 달라도 새 대화를 시작할 필요는 없습니다.

```text
기능은 맞지만 함수가 너무 길어. 기존 스타일에 맞게 분리해줘.
동작은 바꾸지 말고 테스트를 다시 실행해줘.
```

“왜 이 방식을 택했어?”, “대안 두 가지와 장단점을 비교해줘”, “수정 없이 코드 리뷰만 해줘” 같은 요청도 유용합니다. Codex를 자동 완성 도구보다, 조사·구현·테스트·리뷰를 함께 하는 동료로 생각하면 좋습니다.

## 4. 권한과 보안을 안전하게 다루기

Codex는 파일을 수정하거나 명령을 실행할 때 권한을 요청할 수 있습니다. 권한 설정은 크게 두 가지를 결정합니다. 샌드박스는 Codex가 접근 가능한 파일·네트워크 범위를 정하고, 승인은 범위 밖 작업 전에 멈춰 확인을 받을지를 정합니다.

처음에는 기본값인 승인 중심 모드를 유지하세요. 신뢰하는 프로젝트에서 반복 작업을 하게 된 뒤에만 권한 범위를 넓히는 것이 좋습니다. 다음 요청은 특히 한 번 더 확인해야 합니다.

- 파일을 대량 삭제하거나 이름을 바꾸는 명령
- 데이터베이스 변경, 배포, 결제 또는 실제 사용자 데이터 처리
- 비밀 키·비밀번호·개인정보를 파일이나 채팅에 붙여 넣는 일
- 외부 서비스에 메시지, 이슈, PR을 생성하거나 데이터를 전송하는 일

비밀 정보는 대화에 직접 입력하지 말고, 필요하다면 환경 변수·비밀 관리 도구 등 프로젝트의 기존 방식을 사용하세요. Codex에게도 “초안만 만들고 외부에 전송하거나 배포하지 마”, “삭제 전에는 파일 목록을 보여 주고 승인받아”처럼 경계를 분명히 알려줄 수 있습니다.

## 5. 반복해서 쓰게 되면

프로젝트마다 같은 규칙을 매번 설명하게 되면 저장소 최상위에 `AGENTS.md`를 두는 방법이 있습니다. 이 파일에는 프로젝트 구조, 실행·테스트 명령, 코딩 규칙, 금지 사항, 완료 기준을 짧고 정확하게 적습니다. Codex는 해당 지침을 작업 맥락으로 활용할 수 있습니다. CLI에서는 `/init`으로 초안 생성을 시작할 수 있지만, 생성된 내용은 팀의 실제 명령과 규칙에 맞게 꼭 고쳐야 합니다.

반복 업무가 명확해지면 스킬(Skill)로 절차를 묶거나, 충분히 검증된 작업만 예약 작업으로 자동화할 수 있습니다. 다만 처음부터 자동화하기보다 일반 대화에서 여러 번 실행해 결과가 안정적인지 확인한 후 적용하세요.

## 6. 초보자를 위한 바로 쓰는 요청 모음

```text
이 프로젝트를 처음 보는 개발자에게 설명하듯 구조, 실행 방법,
테스트 방법을 정리해줘. 파일은 수정하지 마.
```

```text
이 오류를 재현할 수 있는 테스트가 있는지 찾아줘.
없다면 최소한의 테스트 추가 계획을 제안하고, 내 승인 후에만 수정해줘.
```

```text
현재 작업 트리의 변경 사항을 코드 리뷰해줘.
버그 가능성, 누락된 테스트, 유지보수 위험을 중요도 순으로 알려줘.
수정은 하지 마.
```

```text
이 기능을 구현해줘. 기존 코드 스타일을 따르고 새 의존성은 추가하지 마.
관련 테스트·린트를 실행한 뒤, 변경 파일과 검증 결과를 간단히 보고해줘.
```

처음에는 “수정하지 말고 조사만 해줘”와 “계획을 먼저 보여줘”를 자주 활용해 보세요. Codex의 작업 범위와 결과를 쉽게 파악할 수 있고, 이후에는 더 큰 작업도 자신 있게 맡길 수 있습니다.
